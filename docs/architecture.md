# Architecture

```text
Browser -> React product UI -> Spring Boot API -> FastAPI/LangGraph
             |                    |
             +---- PostgreSQL ----+
              business   checkpoints
```

M3A adds a `frontend/` React and TypeScript application without changing the durable backend boundary. During experience discovery, the browser calls typed product endpoints through one API client and Mock Service Worker intercepts them at the HTTP boundary. Feature components never read fixture records directly. This allows the interaction model to be tested before Company, Job, Soul, Position, Assignment, ContentItem, Activity, and organization APIs become authoritative in M3B.

The three product surfaces are Command Center, Content Studio, and Organization Studio. TanStack Query owns remote state, React Router owns navigation, and React Flow renders organization layout. Organization card coordinates are presentation state; moving a card never implies a reporting or authority change. Mock mode is visibly labelled and can be disabled with `VITE_ENABLE_MOCKS=false` when compatible product APIs exist.

## Job competence and Soul presentation boundary

An Agent Instance receives all professional capability from its Job Definition and current Task Contract: required workflow, tools, evidence, validators, output schema, completion conditions, authority, and quality threshold. Appointment of a different Soul must not change any of these inputs or their enforcement.

Soul is a presentation layer for identity, visual character, voice, and communication style. It may choose between equally valid non-material expressions, but cannot alter factual accuracy, required execution, review, permissions, approval, or the definition of done. Runtime and evaluation tests must prove that the same Job and Task Contract maintain an identical quality floor under every Soul fixture. Employee levels are excluded; style traits are never capability signals.

## Project memory and reassignment boundary

Project progress belongs to durable business and workflow records, not to a Soul or model context window. WorkTask uses Position as the stable accountable owner and the current Assignment as executor attribution. Assignment history records who performed work during each time interval.

```text
Project / WorkTask / Decision / Artifact / Evidence / Activity
                              +
Position playbook / Task Contract / WorkflowRun checkpoint
                              ↓
                     Agent context builder
                              ↓
             current Assignment + appointed Soul
```

Replacing an employee closes the old Assignment, writes an immutable Handoff Snapshot, creates the new Assignment, and emits an auditable reassignment event in one governed operation. The snapshot records objective, completed and active work, remaining actions, blockers, risks, decisions, Artifact and Evidence references, workflow thread/checkpoint, and exact next action. It is an index into authoritative records rather than a second source of truth. The new Agent Instance rebuilds context and resumes the same checkpoint, with idempotency preventing duplicate steps and artifacts.

Spring Boot is authoritative for projects, founder decisions, artifacts, and workflow runs in the PostgreSQL `public` schema. The orchestrator stores only execution checkpoints in the dedicated `langgraph` schema. Thread IDs are generated by the backend and persisted in both stores.

## Start sequence

1. Spring persists a DISCOVERY project and RUNNING workflow run.
2. Spring starts LangGraph with the stable thread ID.
3. LangGraph deterministically analyses the idea, creates a question, calls `interrupt()`, and checkpoints.
4. Spring persists the returned decision and marks the project and run waiting.

## Resume sequence

1. Spring validates and records the selected stored option, then marks the project PRODUCT_DEFINITION.
2. Spring resumes LangGraph using the stored thread ID.
3. LangGraph continues from the PostgreSQL checkpoint and returns deterministic Markdown.
4. Spring stores Product Brief version 1 and marks the run and project completed.

Database constraints enforce valid states, foreign keys, a unique thread per run, and one artifact version per project/type. Duplicate decision resolution is rejected before resume. Slack and model calls are excluded because M1 validates durable human-in-the-loop control flow, not channel or content quality.

## M2 Slack boundary

Slack calls only the Spring Boot integration endpoints. The backend verifies the raw signed request, authorizes the configured workspace and founder, and persists a unique inbox event before acknowledging. A scheduled worker routes the event into authoritative Conversation and Task records. A separate outbox record is then delivered with `chat.postMessage` or `chat.update`. Interrupted claims are restored after restart and transient failures use bounded retry.

```text
Slack -> verified Spring ingress -> PostgreSQL inbox -> routing worker
                                                |          |
                                                v          v
                                       conversation/task  outbox -> Slack Web API
```

The Python orchestrator remains unaware of Slack credentials and delivery. It is called only when an accepted Slack decision action resumes an existing workflow.
